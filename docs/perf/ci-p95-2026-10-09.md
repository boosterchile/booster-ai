# Tiempo de CI por PR — 2026-10-09

Criterio T10-14 (ADR-082): p95 del tiempo de reloj de CI por PR ≤ 10 min sobre los últimos 50 PRs, medido con la API de Actions.

- Repositorio: `boosterchile/booster-ai`
- PRs medidos: 50 (corridas desde 2026-09-27)
- p50: 5,0 min · **p95: 6,6 min** · máximo: 8,1 min
- Resultado: **Cumple** (umbral 10 min)

## Método

- Por cada rama con corridas de `ci.yml` por `pull_request` (`success` o `failure`), se toma la última corrida y su commit.
- El reloj del PR es el del workflow más lento de ese commit entre `ci.yml`, `e2e-pr.yml`, `security.yml`, que corren en paralelo.
- La duración de una corrida es `updated_at - run_started_at` (último intento). Las canceladas por concurrencia no cuentan.
- Reproducible con `GITHUB_TOKEN=... node scripts/repo-checks/medir-ci-p95.mjs`.

## Notas de esta medición

- Medido el 2026-10-09 a las 21:52 UTC. Las corridas salieron de los mismos endpoints de la API de Actions (`GET /repos/{repo}/actions/workflows/{workflow}/runs`), consultados desde la sesión del agente, porque el token de `gh` del sandbox no autenticaba. Se procesaron con las funciones del script, sin cambios.
- La cola antes del arranque no cambia el resultado: medir desde `created_at` en vez de `run_started_at` dio el mismo p95.
- Si en vez del último intento se mide desde el primer arranque del commit, una rama (`claude/trl10-a-e2e-activacion`) sube a 32,9 min, por una re-ejecución manual pedida media hora después. Esa espera no es tiempo de CI, y por eso el método usa el último intento. Con ese criterio alternativo el p95 es 7,1 min y también cumple.
- 41 de las 300 corridas de `ci.yml` del periodo quedaron canceladas por concurrencia (un push nuevo a la misma rama) y no cuentan.
